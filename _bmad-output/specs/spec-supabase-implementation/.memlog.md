- (direction) User requested a BMad spec/plan for implementing Supabase, with plan artifacts placed under plans.
- (capability) CAP-1: Establish a single Supabase backend foundation so the React app can authenticate, query, mutate, and generate typed data access through one configured client.
- (decision) Use slug supabase-implementation and create a BMad spec folder at _bmad-output/specs/spec-supabase-implementation.
- (capability) CAP-2: Implement Supabase Auth with application profiles and role activation so ADMIN and WAREHOUSE_STAFF permissions are derived from database state, not client metadata.
- (capability) CAP-3: Version the warehouse schema through Supabase migrations covering enums, profiles, master data, business documents, movements, ledgers, audit, indexes, triggers, seed data, and generated TypeScript types.
- (capability) CAP-4: Enforce database authorization with RLS, grants, helper functions, and policies that deny anonymous access and check active profile roles for application tables.
- (capability) CAP-5: Move stock, payment, debt, cancellation, return, stocktake, reconciliation, and document-code operations into RPC transactions where each operation validates role, state, quantities, money, idempotency, and audit before commit.
- (capability) CAP-6: Connect frontend features to Supabase through centralized feature APIs, TanStack Query, generated database types, environment validation, and cache invalidation after official RPC results.
- (capability) CAP-7: Verify Supabase behavior with database/integration and e2e tests for RLS, authorization, rollback, concurrent stock updates, idempotency, confirmed-document immutability, payments, reversals, and reconciliation.
- (constraint) Supabase is the primary backend for MVP; do not add a separate backend server unless a documented requirement cannot be met by Auth, PostgreSQL, RLS, RPC, Storage, or Edge Functions.
- (constraint) Frontend is not a security boundary: service_role keys, secrets, trusted role values, stock totals, payment totals, and privileged business logic must not live in Vite client code.
- (constraint) Inventory and financial operations that touch multiple records must be atomic, idempotent where retryable, auditable, and must prevent negative stock or negative debt.
- (constraint) All database schema changes must be migrations; generated TypeScript database types must not be hand-edited.
- (constraint) Use TailAdmin/React project conventions from AGENTS.md: routes in App.tsx, PageMeta on pages, i18n keys for user-facing strings, Tailwind v4 tokens, logical RTL utilities, and existing UI primitives.
- (decision) Non-goals: no separate Express/Nest backend, no ecommerce/payment gateway integration, no multi-warehouse or multi-branch support, no offline-first sync, and no advanced BI pipeline in this Supabase MVP.
- (assumption) Assume the plan should prepare implementation artifacts and task order, not connect to a real Supabase project or install new packages in this run.
